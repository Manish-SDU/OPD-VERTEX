\section{Methodology}

\subsection{Teamwork and Collaboration}

Tasks were distributed in pairs throughout most of the project, which supported collaboration and peer review. The workflow was organized in Trello across five sprints, allowing the team to track and manage tasks as the project evolved.

In Sprint 1, the team focused on planning the project structure by preparing the project proposal, creating initial diagrams, and designing the database. In Sprint 2, the team set up the application environment, designed the first draft of the user interface, configured both SQL and NoSQL databases, and implemented authentication features for patients, doctors, and administrators.

In Sprint 3, the team implemented audio capture and speech-to-text transcription, fixed and improved the database, and prepared the project presentation for the midterm seminar. In Sprint 4, the team implemented document versioning and editing, added email sending functionality, integrated LLM capabilities for transcription, suggestions, and reports, and completed the user interface implementation. In Sprint 5, the team fixed the last bugs, updated the diagrams, created the final seminar presentation, and finished the report.

GitHub was used to share and manage the code, allowing the team to collaborate efficiently while keeping all contributions organized in one place. The team met around twice per week to review progress, coordinate tasks, and resolve blockers. WhatsApp was used mainly for daily updates, while Discord was used for sharing files, data, and other project resources.

\subsection{Scope Context and Source Selection}

During early scoping, the team compared several possible project directions with public SDU and technology sources. The supplied SDU researcher pages for Jacek Fiutowski\footnote{\url{https://portal.findresearcher.sdu.dk/en/persons/fiutowski}}, Casper H\o{}gh Kunstmann\footnote{\url{https://portal.findresearcher.sdu.dk/en/persons/casper-h\%C3\%B8gh-kunstmann}}, and Ayoub Laghrissi\footnote{\url{https://portal.findresearcher.sdu.dk/en/persons/ayoub-laghrissi}} show research activity around nanophotonics, sensing, imaging, microfluidics, nanomaterials, and hyperspectral or spectroscopic monitoring~[6,7,10]. NanoChem describes nanoscale chemical imaging facilities and use cases in materials, environmental, and medico-oriented analysis\footnote{\url{https://www.nanochem.dk/}}~[8]. The imec SNAPSCAN VNIR page describes a hyperspectral evaluation system for laboratory research, food inspection, medical imaging, and material characterization\footnote{\url{https://www.imechyperspectral.com/en/cameras/snapscan-vnir}}~[9], while the DeepHS-Fruit-v2 dataset listing\footnote{\url{https://paperswithcode.com/dataset/deephs-fruit-v2}} represents a dataset-driven benchmark context~[11].

These sources are relevant to the semester context because they illustrate data-intensive sensing and AI workflows, but they are not used as evidence for Med Flow's clinical performance. Instead, they helped clarify the difference between an imaging-model project and this report's actual focus: a local-first software system for consultation audio, transcription, doctor review, document generation, and auditability.

\subsection{Application of Course Knowledge}

\begin{itemize}
	\item \textbf{Artificial Intelligence:} Faster-Whisper transcribes consultation audio, while a local LLM generates draft clinical notes and Suggestive Mode alerts.
	\item \textbf{Component-Based Systems:} FastAPI routers, application services, repositories, and adapters separate authentication, patients, consultations, transcription, review, prescriptions, PDF, email, and audit.
	\item \textbf{Algorithms and Data Structures:} transcript normalization and JSON validation structure raw speech into fields used by review, prescription, and PDF workflows.
	\item \textbf{Designing Software Systems with Embedded Elements:} Docker Compose and local model services were validated against realistic laptop hardware limits instead of relying on cloud APIs.
	\item \textbf{Data Management:} MySQL stores users, patients, consultations, prescriptions, and audit logs, while MongoDB stores transcripts, generated documents, prompts, and email templates.
\end{itemize}
