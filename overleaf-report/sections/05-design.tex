\section{Design}
\label{sec:design}

This chapter describes the design of Med Flow, focusing on the principles used to structure the system, the main components and their interactions, the data model, and the cross-cutting concerns of the application.

\subsection{Design Goals and Principles}
\label{subsec:design-goals-principles}

Med Flow was designed as a privacy-first, locally hosted clinical assistant for outpatient departments. The actors and use cases are defined once in Section~\ref{subsec:actors-use-cases}; this chapter uses them as design inputs and focuses on architectural decisions, component boundaries, data ownership, and workflow design. The design principles translate the privacy and AI-governance concerns from the problem analysis into implementation boundaries\refcite{11,12,14}. Six principles guided the design decisions:

\begin{itemize}
  \item \textbf{Local-first execution:} sensitive processing runs inside the clinic environment, so no consultation data is sent to a third-party cloud LLM.
  \item \textbf{Component-based design:} the system is split into bounded modules, each with its own application service and domain contracts.
  \item \textbf{Loose coupling through ports and adapters:} external dependencies are exposed as domain ports and implemented by adapters, so application logic does not depend on concrete libraries.
  \item \textbf{Replaceability of AI components:} transcription, LLM generation, and suggestive review are independent ports, allowing them to be swapped without changing core application logic.
  \item \textbf{Replaceability of scheduling and identity:} booking and login boundaries can be connected to external clinic or public-sector services without changing the consultation documentation pipeline.
  \item \textbf{Human-in-the-loop approval:} no AI output is written to the relational database without doctor approval.
\end{itemize}

These principles keep the system maintainable through a layered architecture and make it easier to extend because each component can be replaced without rewriting the core.

\subsection{System Overview and Architecture}
\label{subsec:system-overview}

Before writing code, the team sketched the main user journeys and screen layouts in Figma. The mockups were intentionally lightweight because UI design was not the main focus. They were used to agree on how the actor goals from Section~\ref{subsec:actors-use-cases} would appear as screens: unified login, doctor dashboard, appointment scheduling, consultation recording, draft review, patient portal, and administrator configuration. The review page evolved during development and was split into view, editor, and print modes after the team decided to support Markdown editing.

The target architecture is a set of cooperating services organized around the clinical workflow: identity, booking, patient, consultation, transcription, LLM orchestration, suggestive review, PDF generation, notification, and audit. Public endpoints sit behind an API gateway, while AI components run on dedicated local services. Each service owns or accesses data through a clear contract to preserve loose coupling.

In the implemented system, this design is realized on a smaller scale. The logical components live as Python modules inside a single FastAPI application. The transcription module runs as a separate Whisper sidecar, the LLM runs in Ollama, MySQL stores relational data, and MongoDB stores AI documents. All services are packaged as Docker containers and orchestrated with Docker Compose, giving the project a reproducible setup and a clear migration path toward the target architecture.

On the user-facing side, the Doctor Dashboard is the main interface for doctors and gives access to appointments, the patient list, consultation context, recording, draft review, and prescription approval. The Patient Portal is used by patients to log in, book appointments, and read their own consultations and prescriptions. Both interfaces are server-rendered with Jinja2 templates and communicate with the backend through the Gateway API.

Authentication and authorization validate credentials, issue JWT tokens, and enforce role-based access control. The Email Notification Service sends patient summaries through SMTP. The Document Editing and Versioning service manages generated report lifecycle, Markdown edits, and version history so every revision made by a doctor can be traced.

The AI pipeline starts with local audio capture, which sends consultation audio to the Faster-Whisper transcription module\refcite{10}. The LLM Orchestrator manages prompts, retries, and structured output validation. Generation is delegated to the local Ollama runtime configured for Qwen3:8b, and ReportLab renders approved Markdown reports into printable PDFs.

\subsection{Aspect-Oriented Programming for Cross-Cutting Concerns}
\label{subsec:aop-cross-cutting}

Logging, performance measurement, error capture, and request tracing touch almost every layer of the system, but they do not belong to the business logic of any single module. To avoid scattering logging statements throughout the codebase, these concerns are handled with an Aspect-Oriented Programming approach.

The AOP layer is based on a class-level decorator that automatically wraps every public method of a class with entry, exit, and error logging while measuring wall-clock duration. Middleware logs every HTTP request, including method, path, client IP, status code, and duration, without changing route handlers.

This keeps application services and repository classes free of observability boilerplate while producing uniform log entries with consistent duration units. A future migration to tracing or metrics infrastructure would require changing one focused area instead of refactoring the entire codebase.

def apply_logging_aspect(component: str, module: str, *, log_args: bool = False, exclude=frozenset()):
  def decorator(cls: type) -> type:
    aspect = log_method(component, module, log_args=log_args)
    for attr_name in list(vars(cls)):
      if attr_name.startswith("_") or attr_name in exclude:
        continue
      attr = getattr(cls, attr_name)
      if callable(attr):
        setattr(cls, attr_name, aspect(attr))
    return cls
  return decorator

\subsection{Data Design and Dual-Database Architecture}
\label{subsec:data-design}

Med Flow uses a dual-database design to separate the system of record from iterative AI artifacts. The relational store provides consistency for clinically meaningful data, while the document store provides flexibility for evolving AI outputs.

MySQL stores doctors and administrators with roles, hashed passwords, license data, and specialization; patients with demographics, allergies, medical history, and hashed passwords; appointments with patient, doctor, schedule, status, reason, notes, and optional consultation linkage; consultations with status transitions from recording to transcribing, processing, review, approved, rejected, or cancelled; prescriptions with versioning; and append-only audit logs.

MongoDB stores semi-structured artifacts from the AI pipeline: transcripts and working notes, drafted reports, suggestive reviews, generated PDFs, versioned prompt templates, and editable patient communication templates. The iterative and fast-changing artifacts remain in MongoDB, while the legally meaningful approved prescription is moved into MySQL only after doctor approval.

\subsection{Main Workflow and AI Pipeline}
\label{subsec:main-workflow-ai-pipeline}

The consultation flow is implemented as four smaller workflows: appointment scheduling, consultation creation, AI processing, and prescription approval. The booking workflow creates appointment context with patient, doctor, schedule, duration, reason, and status. When the doctor starts the appointment, the backend creates the linked consultation and moves into the recording workflow. The system creates a new record with status \texttt{recording}; audio is captured in the browser and streamed to the backend through a WebSocket, which forwards chunks to the Whisper sidecar in near real time. Partial transcripts are stored so the session can survive a disconnect. When the doctor stops recording, the consultation moves to \texttt{processing} and the AI pipeline starts.

The AI pipeline contains two LLM calls followed by a safety pass. The transcript normalizer converts the raw transcript into structured JSON and filters speech artifacts. The clinical-note generator combines the normalized transcript with patient context, including age, allergies, and medical history, and asks Qwen3:8b to produce a structured object containing presenting problem, relevant history, assessment, medication or treatment plan, patient instructions, follow-up date, requested lab or imaging tests, safety-net advice where supported, and a Markdown rendering of the full report.

Suggestive Mode then performs a second pass. An LLM-based clinical safety review is merged with deterministic rule-based checks, such as missing dose, frequency, duration, allergy conflicts, and contraindication conflicts. The combined output is shown to the doctor as advisory alerts. Nothing is written to the prescription unless the doctor accepts it during editing.

After generation, the doctor opens the review page, optionally edits the Markdown report, and either approves or rejects the draft. If approved, the system builds a prescription, saves it in MySQL with \texttt{is\_approved = true} and the next version number, marks the generated document as approved, and updates the consultation status. After approval, the doctor can download the PDF and send the patient a follow-up email with the exported PDF attached.

\subsection{Privacy, Security and Error Handling}
\label{subsec:privacy-security-error-handling}

The design treats clinical data as information that must not leave the local environment. Speech-to-text and LLM services run locally, so there is no path that sends transcripts or reports to a remote provider. Login is handled with email/password credentials, bcrypt password hashing, and short-lived JWT tokens stored in an HTTP-only cookie. Role-based access control protects routes that mutate clinical content, and patients can see only their own consultations and prescriptions. Patient invitation links, password setup links, and password reset flows are not implemented in the prototype; they are suitable future additions at the identity boundary.

Traceability is split across audit entries, document version history, and workflow status fields. Audit entries include user, role, action, target, IP address, timestamp, and JSON details; administrative prompt and email-template changes use this mechanism. Doctor edits to generated reports are preserved through version history with old and new values, while approval or rejection changes the generated document and consultation status. The manual approval gate ensures that no AI output is written into the relational prescriptions table without explicit doctor approval, and email gating ensures that patient summaries are sent only after approval.

Error handling follows a small predictable model. Domain-level problems raise a \texttt{ValueError}, which the API translates into 400 or 404 responses. Unexpected failures become 500 responses. Transcription errors leave the consultation in its current state so the doctor can retry. LLM errors are caught by validation and drafts are left unchanged. PDF and email failures return 500 without altering the underlying record.

The implementation does not claim full regulatory compliance. TLS termination, stronger service-to-service protection, retention enforcement, and at-rest encryption are treated as future deployment requirements in line with service-security guidance\refcite{17}.

\subsection{UI Overview}
\label{subsec:ui-overview}

The UI is intentionally simple and task-focused. Each screen serves one role and one job, and every page shares a common base layout and CSS bundle. The doctor dashboard is the role-aware home page for clinicians. The consultation page hosts live recording and transcription. The review page is the core human-in-the-loop screen because it shows the AI draft, structured fields, suggestive-mode alerts, Markdown editor, and approve, reject, print, and email actions.

The patient portal is read-only with respect to clinical data. The admin configuration view lets administrators edit prompts and email templates while maintaining an audit trail. Appendix~\ref{app:final-application-screens} collects the final application screenshots, including the patient and doctor appointment views.

\subsection{Scope Decisions and Future Enhancements}
\label{subsec:scope-decisions}

A simple booking and scheduling capability was implemented to support the semester workflow. It lets patients create appointments, lets doctors and administrators handle operational appointment status changes, and lets doctors start a consultation from appointment context. The design still does not treat this internal module as the long-term source of truth for appointments. Clinics, companies, and public authorities often already operate booking systems connected to identity and access infrastructure. In Denmark, MitID provides national eID for public self-service solutions, while NemLog-in provides public-sector login and single sign-on for authority self-service systems\refcite{5,6}. MitID Erhverv also supports organisational identities where employees can act digitally on behalf of an organisation\refcite{18}.

For this reason, Med Flow keeps scheduling behind a replaceable boundary even though a local appointment module is implemented. The current module creates the consultation shell directly from internal appointment data; a production booking service could provide the same shell through an adapter containing patient, clinician, time, and visit-type metadata. Med Flow can then take over from the moment the consultation begins: recording, transcription, AI-assisted drafting, review, approval, PDF export, and follow-up communication. This keeps the documentation pipeline independent from the appointment provider.

Figure~\ref{fig:booking-identity-integration} uses a MitID booking scenario to show the intended boundary in a simpler form. The first step is outside Med Flow: the patient uses MitID in a clinic booking portal, and the clinic system records that a verified patient has booked a specific appointment. The second step is the handoff into Med Flow: a replaceable adapter translates the appointment data into the simple consultation shell that Med Flow needs before the doctor starts recording.

For example, a patient signs in with MitID and books a follow-up visit with a doctor at 09:30. The external booking system owns the login, appointment confirmation, and calendar slot. The adapter then sends Med Flow only the useful consultation context: patient, doctor, time, visit type, and reason for visit. Med Flow can then open the consultation workflow without being responsible for MitID or the clinic's booking platform.

Future enhancements include a queued retry layer for transient Whisper or Ollama failures, hardened deployment security, expanded Suggestive Mode rules with a broader interaction database, patient onboarding and password-reset links, and production-grade adapters that can feed or replace the internal scheduling module with external booking, identity, and access-control services.
