\section{Implementation}
\label{sec:implementation}

This chapter describes how the design was implemented in the codebase. The system follows a component-based architecture with a FastAPI backend, MySQL and MongoDB persistence, Faster-Whisper transcription\refcite{10}, local Ollama/Qwen3:8b generation, ReportLab PDF generation, and SMTP email delivery. The application is containerized with Docker Compose for repeatable local deployment. Runtime settings are loaded through Pydantic settings, while logging and request tracing are handled by the project's middleware and aspect infrastructure.

\subsection{Booking and Scheduling Implementation}
\label{subsec:booking-scheduling-implementation}

The booking and scheduling flow is implemented as a lightweight internal module rather than as a production external appointment provider. The appointment domain model contains patient ID, doctor ID, scheduled time, duration, status, reason, optional notes, and an optional \texttt{consultation\_id}. Status values cover pending, confirmed, cancelled, completed, and no-show appointments.

\texttt{AppointmentApplicationService} owns the business rules. It filters appointment lists by role, prevents exact double-booking for the same doctor and time, confirms or cancels appointments, records no-shows, and starts a consultation from an appointment. Starting a consultation creates a consultation row using the appointment patient and reason, links the appointment to that consultation, and marks the appointment as completed.

The FastAPI route module \path{appointments.py} exposes the HTML workflow: appointment list, booking form, detail page, confirm, cancel, no-show, and start-consultation actions. Role checks keep clinical actions restricted: doctors can start consultations, doctors and administrators can perform operational appointment actions, and patients can only book for themselves or view their own appointment list. The SQL implementation is backed by the \path{appointments} table introduced in Alembic revision \path{20260520_0002}, while the in-memory repository supports deterministic unit and RBAC tests.

\subsection{Authentication and Authorization}
\label{subsec:authentication-authorization}

Authentication ensures secure access control using role-based authorization. The system uses FastAPI dependency injection, JWT tokens, bcrypt password verification, and a modular service structure. Doctors, administrators, and patients all authenticate through the same login route with email/password credentials; there is no implemented workflow where a doctor generates a patient password link or URL-based login token. The doctor's patient email action sends approved follow-up content and the exported PDF attachment, not a login link. This internal login is sufficient for the semester implementation, while the architecture keeps identity at a boundary where a Danish deployment could add patient invitation links or integrate with MitID/NemLog-in through a dedicated adapter\refcite{5,6}.

The main authentication logic is implemented in \texttt{AuthApplicationService}, which bridges the API layer and domain logic. Domain models represent users, login requests, and the authentication interface, creating a consistent contract between application and infrastructure layers.

\begin{itemize}
  \item \textbf{User:} represents a system user with roles.
  \item \textbf{LoginRequest:} encapsulates login credentials.
  \item \textbf{AuthService:} defines an abstract interface for authentication logic and allows alternative implementations.
\end{itemize}

The interface and application-service bridge are shown in \figref{fig:implementation-auth-service}, where authentication remains replaceable behind the domain contract.

After successful authentication, the system assigns a JWT to the user. The token is used for later authenticated requests and includes user identity and role. Authentication checks are enforced through FastAPI dependencies that validate JWTs from incoming requests and ensure that only authenticated users can reach protected endpoints. Route-level checks separate operational and clinical actions: administrators can manage configuration and perform appointment operations such as confirmation or no-show marking, while report generation, report editing, suggestive review, consultation start, prescription approval, and rejection remain doctor-only clinical actions.

\subsection{Transcription Module}
\label{subsec:transcription-module}

The transcription component enables live conversion of audio into text, which can then be processed into clinical documentation. It is designed to be scalable, replaceable, and integrated with the other components.

The transcription application service handles streaming audio data, temporary audio and text chunks, and finalization of the complete transcription. The route module \path{transcriptions.py} exposes session start, WebSocket streaming, completion endpoints, and demo-text injection for presentations. The actual speech-to-text conversion is handled by Faster-Whisper through the local Whisper adapter, which communicates with the microservice configured by \path{WHISPER_API_URL}. \figref{fig:implementation-transcription-service} shows the adapter reading this endpoint and sending session requests to the sidecar service.

\begin{enumerate}
  \item \textbf{Session initialization:} temporary storage is created for incoming audio data through \texttt{start\_transcription\_session}.
  \item \textbf{Audio streaming and chunk handling:} audio is streamed to the backend. The service processes chunks and sends them to the Faster-Whisper API for transcription. Partial results are stored using the temporary transcript chunk repository.
  \item \textbf{Transcript assembly:} temporary chunks are assembled into the final transcription, which is then stored in MongoDB as a consultation document.
  \item \textbf{Error handling:} the module handles network interruptions, partial uploads, and API errors. Temporary storage ensures that progress is not lost if a session is interrupted.
\end{enumerate}

\subsection{LLM Orchestration}
\label{subsec:llm-orchestration}

The LLM orchestration component enables transcript normalization, clinical note generation, and suggestions using the locally integrated Ollama model. The implementation uses an Ollama client for low-level HTTP communication and adapter classes in \path{ollama_adapter.py} for domain-specific tasks. Separate adapters return the normalized transcript, validated clinical notes, and structured suggestive review.

The configured runtime endpoint and model are read from \path{LOCAL_LLM_ENDPOINT} and \path{LLM_MODEL_NAME}. In the current implementation, \path{app/core/config.py} validates \path{LLM_MODEL_NAME} as \path{qwen3:8b}; the model comparison in \secref{subsec:model-selection} explains why that model was selected. Prompt templates stored in the prompt repository are populated with patient context, consultation metadata, transcript content, and doctor information before being sent to Ollama. This local execution supports the privacy and AI risk-management goals discussed earlier\refcite{11,12}. The local client setup and JSON generation path are shown in \figref{fig:implementation-ollama-client-setup}.

def generate_json(self, *, system_prompt: str, user_prompt: str,
          temperature: float, max_tokens: int) -> dict[str, Any]:
  raw_response = self._generate_once(system_prompt=system_prompt,
                     user_prompt=user_prompt,
                     temperature=temperature,
                     max_tokens=max_tokens)
  parsed = self._parse_json(raw_response)
  if parsed is not None:
    return parsed
  repaired = self._parse_json(self._repair_json(raw_response=raw_response,
                          temperature=temperature,
                          max_tokens=max_tokens))
  if repaired is None:
    raise OllamaClientError("Qwen3 returned malformed JSON twice.")
  return repaired

The orchestration workflow is:

\begin{enumerate}
  \item \textbf{Prompt construction:} templates are populated with patient context and consultation content.
  \item \textbf{Request dispatch:} the prompt is sent through \texttt{OllamaClient}, which handles retries, timeouts, and errors.
  \item \textbf{Response handling:} \texttt{OllamaClient.generate\_json} extracts JSON, attempts one repair pass for malformed JSON, and returns structured data to the calling service.
  \item \textbf{Error handling:} network errors, model unavailability, and malformed responses are handled by the orchestration layer to provide informative errors.
\end{enumerate}

\subsection{PDF Generation}
\label{subsec:pdf-generation}

PDF generation is implemented with ReportLab. The resulting file is stored in the configured PDF output directory and returned to the browser as a PDF response. \figref{fig:implementation-pdf-generator-setup} shows the adapter creating the output directory, rendering the document, and returning the generated file path.

class ReportLabPdfGenerator(PdfGenerator):
  def __init__(self):
    self.settings = get_settings()
    self.pdf_output_dir = Path(self.settings.pdf_output_dir)
    self.pdf_output_dir.mkdir(parents=True, exist_ok=True)

  def generate_report_pdf(self, report_markdown: str,
              consultation_metadata: ConsultationMetadata) -> str:
    if not report_markdown or not report_markdown.strip():
      raise ValueError("Report markdown cannot be empty")

    last = (consultation_metadata.patient_name or "unknown").strip().split()[-1]
    safe_last = re.sub(r"[^a-z0-9]", "", last.lower()) or "unknown"
    date_str = (
      consultation_metadata.consultation_date.strftime("%Y%m%d")
      if consultation_metadata.consultation_date
      else datetime.now().strftime("%Y%m%d")
    )
    filename = f"report_{safe_last}_{date_str}_{consultation_metadata.consultation_id}.pdf"
    file_path = self.pdf_output_dir / filename
    usable_w = A4[0] - 1.5 * inch

    doc = SimpleDocTemplate(str(file_path), pagesize=A4,
                rightMargin=0.75 * inch, leftMargin=0.75 * inch)
    flowables = [_build_banner(consultation_metadata, usable_w),
           _build_info_card(consultation_metadata, usable_w),
           *_parse_content(report_markdown)]
    doc.build(flowables, onFirstPage=_footer_cb, onLaterPages=_footer_cb)

    if not file_path.exists():
      raise IOError(f"Failed to create PDF at {file_path}")
    return str(file_path)

\subsection{Email Notification Service}
\label{subsec:email-notification-service}

The email notification service sends patient-friendly follow-up information after doctor approval. The report-send action calls the review application service, which refuses unapproved generated reports, loads the patient email address, checks that an exported PDF exists, builds a summary containing prescription, follow-up, and suggestions, attaches the latest exported PDF, and passes the message to the SMTP adapter.

Email sending is handled by \texttt{SmtpEmailService}. It constructs multipart messages using Python's \texttt{email.mime} package and sends them with \texttt{smtplib}. The SMTP adapter supports plain text, optional HTML, and optional attachments; the current patient follow-up workflow sends a plain-text summary with the exported PDF attached. During development, MailHog was used as the SMTP server so outgoing emails could be inspected without sending real messages. \figref{fig:implementation-email-sender} shows this SMTP adapter and its development fallback, and \figref{fig:app-mailhog-screen} documents the captured development inbox.

class SmtpEmailService(EmailService):
  def send_email(self, message: EmailMessage) -> dict:
    msg = MIMEMultipart("mixed")
    msg["Subject"] = message.subject
    msg["From"] = f"{self.from_name} <{self.from_email}>"
    msg["To"] = str(message.to_email)

    alt = MIMEMultipart("alternative")
    alt.attach(MIMEText(message.text_body or "", "plain", "utf-8"))
    msg.attach(alt)

    if message.attachment:
      part = MIMEApplication(message.attachment.data,
                   Name=message.attachment.filename)
      part["Content-Disposition"] = f'attachment; filename="{message.attachment.filename}"'
      msg.attach(part)

    # Plain SMTP is used for MailHog on port 1025 in development.
    with smtplib.SMTP(self.host, self.port) as server:
      server.send_message(msg)
    return {"status": "sent", "provider": "smtp-dev", "host": self.host}

\subsection{Database Integration}
\label{subsec:database-integration}

The system uses a dual-database architecture to manage structured and unstructured data. MySQL is used for structured data such as user accounts, patient records, appointments, consultations, prescriptions, and audit logs. MongoDB is used for semi-structured data such as clinical documents, consultation transcripts, generated reports, and finalized AI artifacts.

SQLAlchemy manages the MySQL connection and session lifecycle. Reusable database access is provided through functions such as \texttt{get\_engine()} and \texttt{get\_session()}. PyMongo manages MongoDB connections, with \texttt{get\_database()} returning the database handle used by document repositories. \figref{fig:implementation-database-connection-setup} shows the two connection helpers that keep SQL and document persistence behind small factory functions.

Both databases are abstracted behind repository classes. SQL repositories in \path{app/infrastructure/db/sql/repositories/sql_repos.py} manage relational records, including appointment rows and their links to consultations. Mongo repositories in \path{app/infrastructure/db/mongo/repositories/mongo_repos.py} manage prompts, templates, consultation documents, and generated artifacts. The test suite can swap these adapters for in-memory repositories, which is why the same application services can be tested without starting MySQL, MongoDB, Whisper, or Ollama.

Auditability is implemented through two complementary mechanisms. \texttt{AuditApplicationService} appends SQL audit entries containing user ID, role, action, target table, target ID, JSON details, IP address, and timestamp. The current admin routes record prompt and email-template updates with explicit action names such as \path{ADMIN_PROMPT_UPDATED} and \path{ADMIN_EMAIL_TEMPLATE_UPDATED}. Doctor-facing report edits are traced through \texttt{DocumentEditingService}, which records field-level old and new values, edit timestamps, and version-history snapshots before each change. Approval and rejection are then represented as generated-document and consultation status transitions. This matches NF-6 as traceability across audit log entries, version history, and workflow state rather than as a single logging table for every event.

\subsection{Runtime Configuration and Observability}
\label{subsec:runtime-configuration-observability}

Runtime configuration is centralized in \path{app/core/config.py}. The most important settings are grouped by responsibility:

\begin{itemize}
  \item \textbf{AI services:} \path{LOCAL_LLM_ENDPOINT}, \path{LLM_MODEL_NAME}, and \path{WHISPER_API_URL}.
  \item \textbf{Email delivery:} \path{SMTP_HOST}, \path{SMTP_PORT}, \path{SMTP_FROM}, and \path{SMTP_FROM_NAME}.
  \item \textbf{Persistence:} \path{MYSQL_DB} and \path{MONGO_DB}.
\end{itemize}

The application currently supports \path{qwen3:8b} as the validated local LLM configuration, while the benchmark table documents other candidates that were evaluated before selecting it.

Observability is implemented through request middleware and aspect decorators. The middleware logs HTTP method, path, client IP, status code, and duration. The \texttt{apply\_logging\_aspect} decorator wraps public service methods with entry, exit, error, and duration logging. Keeping this behavior outside the business logic follows the same separation-of-concerns principle as the repository and adapter boundaries, and it supports later production hardening work such as centralized metrics and tracing\refcite{17}.

\subsection{Deployment and Containerization}
\label{subsec:deployment-containerization}

To make the local setup consistent, reproducible, and portable across developer machines, the Med Flow application is containerized with Docker Compose. The Compose setup starts the backend, databases, AI services, and supporting tools as isolated containers rather than requiring each dependency to be installed manually on the host machine. This is the implemented deployment view of the runtime architecture described in the design chapter.

\figref{fig:deployment-containerization} shows the deployment architecture. Docker Desktop provides the Linux container runtime on the developer workstation, and the services communicate over TCP ports inside the Compose environment. The \texttt{app} container exposes the FastAPI backend on port 8000. The Whisper API provides GPU-accelerated speech-to-text on port 8001, while Ollama hosts the local \texttt{qwen3:8b} model on port 11434 for AI prompts and responses. MySQL stores structured data such as patients, appointments, and consultations on port 3306. MongoDB stores semi-structured clinical notes, generated documents, and audit-related artifacts on port 27017. MailHog supports email testing by accepting SMTP traffic on port 1025 and exposing a web inbox on port 8025.
