\section{Implementation}
\label{sec:implementation}

This chapter describes how the design was implemented in the codebase. The system follows a component-based architecture with a FastAPI backend, MySQL and MongoDB persistence, Faster-Whisper transcription\refcite{11}, local Ollama/Qwen3:8b generation, ReportLab PDF generation, and SMTP email delivery. The application is containerized with Docker Compose for repeatable local deployment. Runtime settings are loaded through Pydantic settings, while logging and request tracing are handled by the project's middleware and aspect infrastructure.

\subsection{API Layer and Routing}
\label{subsec:api-layer}

The API layer is built using FastAPI. It defines and serves HTTP endpoints and acts as the main entry point for browser and API interactions. The central registration point is \texttt{app/api/router.py}, which includes the actual route modules \texttt{auth}, \texttt{dashboard}, \texttt{llm}, \texttt{patients}, \texttt{consultations}, \texttt{review}, \texttt{prescriptions}, \texttt{admin}, \texttt{transcriptions}, and \texttt{profile}. PDF download and email sending are not standalone routers in the current implementation; they are actions inside the review workflow.

\subsection{Authentication and Authorization}
\label{subsec:authentication-authorization}

Authentication ensures secure access control using role-based authorization. The system uses FastAPI dependency injection, JWT tokens, bcrypt password verification, and a modular service structure. This internal login is sufficient for the semester implementation, while the architecture keeps identity at a boundary where a Danish deployment could integrate with MitID/NemLog-in through a dedicated adapter\refcite{14,15}.

The main authentication logic is implemented in \texttt{AuthApplicationService}, which bridges the API layer and domain logic. Domain models represent users, login requests, and the authentication interface, creating a consistent contract between application and infrastructure layers.

\begin{itemize}
  \item \textbf{User:} represents a system user with roles.
  \item \textbf{LoginRequest:} encapsulates login credentials.
  \item \textbf{AuthService:} defines an abstract interface for authentication logic and allows alternative implementations.
\end{itemize}

After successful authentication, the system assigns a JWT to the user. The token is used for later authenticated requests and includes user identity and role. Authentication checks are enforced through FastAPI dependencies that validate JWTs from incoming requests and ensure that only authenticated users can reach protected endpoints. Route-level checks then restrict sensitive actions such as report editing, approval, and email sending to doctors and administrators.

\subsection{Transcription Module}
\label{subsec:transcription-module}

The transcription component enables live conversion of audio into text, which can then be processed into clinical documentation. It is designed to be scalable, replaceable, and integrated with the other components.

The transcription application service handles streaming audio data, temporary audio and text chunks, and finalization of the complete transcription. The route module \path{transcriptions.py} exposes session start, WebSocket streaming, completion endpoints, and demo-text injection for presentations. The actual speech-to-text conversion is handled by Faster-Whisper through the local Whisper adapter, which communicates with the microservice configured by \path{WHISPER_API_URL}.

\begin{enumerate}
  \item \textbf{Session initialization:} temporary storage is created for incoming audio data through \texttt{start\_transcription\_session}.
  \item \textbf{Audio streaming and chunk handling:} audio is streamed to the backend. The service processes chunks and sends them to the Faster-Whisper API for transcription. Partial results are stored using the temporary transcript chunk repository.
  \item \textbf{Transcript assembly:} temporary chunks are assembled into the final transcription, which is then stored in MongoDB as a consultation document.
  \item \textbf{Error handling:} the module handles network interruptions, partial uploads, and API errors. Temporary storage ensures that progress is not lost if a session is interrupted.
\end{enumerate}

\subsection{LLM Orchestration}
\label{subsec:llm-orchestration}

The LLM orchestration component enables transcript normalization, clinical note generation, and suggestions using the locally integrated Ollama model. The implementation uses an Ollama client for low-level HTTP communication and adapter classes in \path{ollama_adapter.py} for domain-specific tasks. Separate adapters return the normalized transcript, validated clinical notes, and structured suggestive review.

The configured runtime endpoint and model are read from \path{LOCAL_LLM_ENDPOINT} and \path{LLM_MODEL_NAME}. In the current implementation, \path{app/core/config.py} validates \path{LLM_MODEL_NAME} as \path{qwen3:8b}; the model comparison in Section~\ref{subsec:model-selection} explains why that model was selected. Prompt templates stored in the prompt repository are populated with patient context, consultation metadata, transcript content, and doctor information before being sent to Ollama. This local execution supports the privacy and AI risk-management goals discussed earlier\refcite{5,12}.

The orchestration workflow is:

\begin{enumerate}
  \item \textbf{Prompt construction:} templates are populated with patient context and consultation content.
  \item \textbf{Request dispatch:} the prompt is sent through \texttt{OllamaClient}, which handles retries, timeouts, and errors.
  \item \textbf{Response handling:} \texttt{OllamaClient.generate\_json} extracts JSON, attempts one repair pass for malformed JSON, and returns structured data to the calling service.
  \item \textbf{Error handling:} network errors, model unavailability, and malformed responses are handled by the orchestration layer to provide informative errors.
\end{enumerate}

\subsection{PDF Generation}
\label{subsec:pdf-generation}

The PDF generation module creates structured PDF documents from clinical data produced by consultations and prescriptions. This feature is important for shareable and printable records.

PDF generation is implemented with ReportLab. The review route \texttt{/review/\{consultation\_id\}/pdf} calls \texttt{ReportPdfApplicationService.generate\_report\_pdf()}, which loads the generated Markdown report from the document repository, fetches consultation, patient, and clinician metadata, and delegates rendering to \texttt{ReportLabPdfGenerator}. The resulting file is stored in the configured PDF output directory and returned to the browser as an \texttt{application/pdf} response.

\subsection{Email Notification Service}
\label{subsec:email-notification-service}

The email notification service sends patient-friendly follow-up information after doctor approval. The implemented endpoint is \texttt{/review/report/\{consultation\_id\}/send-email}, which calls \texttt{ReviewApplicationService.send\_report\_to\_patient()}. That service refuses to send unapproved generated reports, loads the patient email address, builds a summary containing prescription, follow-up, and suggestions, and passes an \texttt{EmailMessage} to \texttt{SmtpEmailService}.

Email sending is handled by \texttt{SmtpEmailService}. It constructs multipart messages using Python's \texttt{email.mime} package and sends them with \texttt{smtplib}. The SMTP adapter supports plain text, optional HTML, and optional attachments, but the current patient follow-up workflow sends a plain-text summary without attaching the PDF. During development, MailHog was used as the SMTP server so outgoing emails could be inspected without sending real messages.

\subsection{Database Integration}
\label{subsec:database-integration}

The system uses a dual-database architecture to manage structured and unstructured data. MySQL is used for structured data such as user accounts, patient records, consultations, prescriptions, and audit logs. MongoDB is used for semi-structured data such as clinical documents, consultation transcripts, generated reports, and finalized AI artifacts.

SQLAlchemy manages the MySQL connection and session lifecycle. Reusable database access is provided through functions such as \texttt{get\_engine()} and \texttt{get\_session()}. PyMongo manages MongoDB connections, with \texttt{get\_database()} returning the database handle used by document repositories.

Both databases are abstracted behind repository classes. SQL repositories in \path{app/infrastructure/db/sql/repositories/sql_repos.py} manage relational records. Mongo repositories in \path{app/infrastructure/db/mongo/repositories/mongo_repos.py} manage prompts, templates, consultation documents, and generated artifacts. The test suite can swap these adapters for in-memory repositories, which is why the same application services can be tested without starting MySQL, MongoDB, Whisper, or Ollama.

\subsection{Runtime Configuration and Observability}
\label{subsec:runtime-configuration-observability}

Runtime configuration is centralized in \path{app/core/config.py}. The most important settings are grouped by responsibility:

\begin{itemize}
  \item \textbf{AI services:} \path{LOCAL_LLM_ENDPOINT}, \path{LLM_MODEL_NAME}, and \path{WHISPER_API_URL}.
  \item \textbf{Email delivery:} \path{SMTP_HOST}, \path{SMTP_PORT}, \path{SMTP_FROM}, and \path{SMTP_FROM_NAME}.
  \item \textbf{Persistence:} \path{MYSQL_DB} and \path{MONGO_DB}.
\end{itemize}

The application currently supports \path{qwen3:8b} as the validated local LLM configuration, while the benchmark table documents other candidates that were evaluated before selecting it.

Observability is implemented through request middleware and aspect decorators. The middleware logs HTTP method, path, client IP, status code, and duration. The \texttt{apply\_logging\_aspect} decorator wraps public service methods with entry, exit, error, and duration logging. Keeping this behavior outside the business logic follows the same separation-of-concerns principle as the repository and adapter boundaries, and it supports later production hardening work such as centralized metrics and tracing\refcite{13}.
